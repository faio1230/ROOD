# PortAudio実機検証

対象はPortAudio v19.7.0です。`scripts/bootstrap-portaudio.ps1` はWASAPIだけを有効にします。`scripts/bootstrap-portaudio-asio.ps1` はSteinberg公式ASIO SDK 2.3.4をローカルで使い、ASIOとWASAPIを有効にした**検証用**ビルドを作ります。この検証版には、`ROOD_ASIO_ONLY` で単一ドライバに絞る[小さなパッチ](../patches/portaudio-v19.7.0-asio-allowlist.patch)を当てています。

## 初回の観測

- デバイス列挙: Windows WASAPI出力14件、各デバイスのPortAudio上限は2チャンネル。
- VB-Audio Virtual Cable（列挙時のID 12）、48 kHz / float32 / 2 ch: `Pa_IsFormatSupported` は共有・排他とも対応。
- 3秒間の無音出力: 共有303 callback、underflow 0、DAC時刻の後退0、報告された出力遅延22 ms。
- 3秒間の無音出力: 排他302 callback、underflow 0、DAC時刻の後退1、報告された出力遅延12 ms。
- 同じWASAPI排他での5秒再試験: 502 callback、underflow 0、DAC時刻の後退1。最初の後退はcallback 2で約1.6 msでした。
- ASIO全ドライバを読み込む通常ビルドはこのPCでデバイス列挙が停止しました。登録されたどのドライバで止まるかは未特定です。検証用パッチで1ドライバに限定すると列挙できました。
- VB-Matrix VASIO-8: 8チャンネル、44.1 kHzで5秒の無音出力が成功（243 callback、underflow 0、時刻後退0）。報告遅延は約23.22 ms。
- VB-Matrix VASIO-32: 16チャンネルと32チャンネル、44.1 kHzでそれぞれ3秒の無音出力が成功（各146 callback、underflow 0、時刻後退0）。報告遅延は約23.22 ms。
- VASIO-8の48 kHz / 8チャンネルは形式照会が対応と返しましたが、`Pa_OpenStream` は `Invalid sample rate` で失敗しました。
- MSVC版PortAudioでも、VASIO-32の32チャンネル、44.1 kHzで3秒の無音出力が成功しました。146 callback、underflow 0、DAC時刻の後退0、報告遅延23.22 msでした。
- その後、コールバックが消費したフレーム総数を壁時計で割って確認しました。VASIO-32の32チャンネル・44.1 kHzは10秒で247,296フレーム、**実効約24,528 frames/s**でした。PortAudioの報告レート44,100 Hzと大きく異なり、underflowと時刻後退は0でした。VASIO-32の16チャンネルとVASIO-8の8チャンネルも約24,400 frames/sです。同じ計測をした別の仮想WASAPI出力は48,000 Hzに対し約48,085 frames/sでした。PortAudioが返す時刻の連続性だけではクロック速度の誤りを発見できません。
- 別のVB-Audioドライバ `Voicemeeter Virtual ASIO` でも、8チャンネル・44.1 kHzの形式照会と開設は成功しました。しかし現行MSVCプローブで10秒間に249,344フレーム、**実効約24,764 frames/s**でした。underflowと時刻後退は0で、5%超の速度差を理由にプローブは終了コード1を返しました。48 kHzは形式照会で対応と出ましたが、開設時に `Invalid sample rate` で失敗しました。このPCではVB-Matrix以外の仮想ASIOでも速度異常と形式照会・開設の不一致が再現します。
- Realtek ASIOは8出力チャンネルを列挙し、48 kHz・44.1 kHzの8チャンネルと48 kHzの2チャンネルを形式照会で対応と返しました。しかし3条件とも開設時に `Invalid sample rate` で失敗しました。一時的にPortAudioの詳細ログを有効にした検査では `ASIOGetSampleRate` が0 Hzを返し、`ASIOSetSampleRate(48000)` はハードウェア入出力が存在しないか利用できないとして拒否されました。通常の検証用DLLは詳細ログOFFへ戻しました。
- 登録済みのDante Virtual Soundcard、Blackmagic Audio、ASIO MADIface USB、D8 SC ASIO Driverをドライバ名で限定して列挙しましたが、このPCで利用できるASIO出力デバイスとしては現れませんでした。登録情報だけでは接続中の実機や利用可能なチャンネルを証明できません。
- MSVC版WASAPIでVB-Audio Virtual Cable（ID 12）の共有・排他を48 kHz / 2チャンネルで3秒ずつ再試験しました。共有303 callback、排他302 callback、どちらもunderflow 0。DAC時刻はcallback 2で共有が約8.0 ms、排他が約1.6 ms後退しました。報告遅延は共有22 ms、排他12 msでした。

WASAPI排他モードで時刻が後退したため、`outputBufferDacTime` を無条件に連続時刻として使う設計にはしません。ASIOについても `Pa_IsFormatSupported` の結果だけでは開設可否を決められません。これらの数値はドライバ・機器・同時利用状況に依存します。無音出力が成功しても、各チャンネルの実際の行き先、物理DAC時刻、長時間ドリフトは未検証です。

### 仮想ケーブル録音によるWASAPI経路の確認

`scripts/test-wasapi-cable-capture.ps1` でROODのSRT受信試験を動かし、出力先の `CABLE Input (VB-Audio Virtual Cable)` と対になる `CABLE Output` を別のFFmpegプロセスで48 kHz・ステレオPCMとして録音しました。`scripts/analyze-cable-capture.py` はPython標準ライブラリだけで1秒ごとの440 Hz、330 Hz、880 Hz成分を測ります。共有と排他をそれぞれ実行し、最初の接続では440 Hzが左、5.1トラックの6番目から取った330 Hzが右に届き、再接続後は880 Hzが左に届いて右が無音であることを確認しました。両モードとも、最初の接続でPortAudio underflow 0、音声フレーム破棄0、再接続2回・切断2回です。録音ファイルと受信ログは `build/tests/wasapi-cable-{shared,exclusive}` と `build/tests/wasapi-cable-loopback-{shared,exclusive}` に保存されます。

この試験はPortAudioコールバックの数値に加え、仮想デバイスの録音端までの信号とチャンネル割り当てを確認します。物理DACへの配線、実際のDAC時刻、ASIO出力や別クロックでの長時間同期は対象外です。

## 採用を確定するための検証

### SRT受信から音声出力までの短時間試験

MPEG-TSの映像1本、ステレオ音声1本、5.1音声1本をSRTで5秒間送り、切断後に別の3秒入力を再接続するループバック試験を追加しました。ROODは48 kHz音声を時刻付きキューに配置し、任意のトラック／チャンネル経路でPortAudioへ出力します。このPCのVB-Audio仮想デバイスで、WASAPI共有・排他の2チャンネル出力、およびASIOの32チャンネル・44.1 kHz出力を確認しました。ASIOでは48→44.1 kHzの変換を通しています。いずれもPortAudioコールバックがデコード済みフレームを消費し、短時間の試験ではデバイスunderflowは0でした。

5.1トラックの6番目のチャンネルには330 Hzの識別信号を入れ、OMT受信プローブで指定した2番目の出力チャンネルに非無音サンプルが届くことを確認しました。PortAudio側の物理出力先はこの試験だけでは確認できません。ASIOは検証用の単一ドライバ許可パッチを使っています。出力時刻後退はWASAPIで観測されました。クロック差補正は初期実装です。別クロックの実機による長時間同期と機器切断復帰は引き続き未検証です。

ASIOの30秒連続受信では、VASIO-32の申告44.1 kHzと実効約24.6 kframes/sの差により、音声フレームの大半が時刻付きキューから破棄され、Spout映像も大量に遅延破棄されました。Releaseビルドの20秒再試験でも同じ結果でした。最初の接続で音声433,823フレーム再生、879,648フレーム破棄、Spout映像497フレーム受信中379フレーム破棄です。30秒以上のループバック試験はこの状態を失敗と判定するよう変更しました。このVB-Matrix仮想ASIO環境ではPortAudioのASIO出力を採用確定できません。ドライバ設定と別のASIO実機で、申告レートと実効コールバック速度を再測定します。

30秒のWASAPI共有ループバックでは、補正器が5秒の基準測定後に有効になり、終盤の推定補正量は約−58 ppm、基準からの音声キュー先行量変化は約2.9 msでした。PortAudio underflowと時刻付きキューの破棄は0です。実際の送信側とデバイスのクロック差を外部基準で測った値ではありません。±100 ppmの仮想クロック差を1時間分進める単体試験では、補正量が逆方向へ収束し、先行量の誤差が20 ms以内でした。

`scripts/test-srt-clock-drift.ps1` では、FFmpegの `-readrate` でSRT送信を公称速度から±300 ppmずらし、最初の接続を各180秒続けました。WASAPIの仮想ケーブルへ音声を、Spoutへ映像を同時出力した結果、速い送信 `1.0003` では終盤の補正量が約−308 ppm、遅い送信 `0.9997` では約＋311 ppmでした。両試験とも最初の接続で音声underflow・音声フレーム破棄・Spout映像破棄・Spout送信失敗は0です。ログ上のキュー先行量の基準からの誤差は最大16.34 ms／15.73 ms、Spoutと音声の推定時差は最大14.95 ms／15.95 msでした。試験後のSRT切断・再接続も通りました。スクリプトは補正量の方向と目標±100 ppm以内、誤差・破棄・時刻異常の上限を自動判定し、`build/tests/<LogName>/drift-summary.txt` に結果を保存します。送信、受信、音声デバイスが同じPC上にある模擬速度差試験であり、独立クロックの実機間や物理出力時刻を検証したものではありません。

ReleaseビルドでSRT受信遅延20 ms、受信バッファ容量256 KiB、音声・Spout出力遅延各100 msを設定し、別の仮想WASAPIデバイスへ20秒間ループバックしました。最初の接続で音声910,785フレーム、Spout映像474フレームを出力し、PortAudio underflow、音声フレーム破棄、Spout映像破棄はいずれも0でした。ログ上のSpoutと音声メディア時刻の最大差は約5.1 msです。この差はアプリ内の推定値であり、物理的な出力間の時差や送受信の総遅延を示しません。

同じReleaseビルドでWASAPI、Spout、32チャンネルOMTを同時に20秒間出力しました。最初の接続で音声900,225フレーム、Spout映像469フレームを出力し、PortAudio underflowと音声・Spoutフレーム破棄は0でした。OMT受信器は映像346フレームと32チャンネル音声693パケットを取得し、0番・31番の信号を確認しました。これらは同一PCの短時間試験です。

同じ3出力を150秒間動かした別試験では、最初のSRT接続で音声7,139,265フレーム、Spout映像3,719フレーム、OMT映像3,719フレームと音声7,437パケットを出力しました。PortAudio underflow、音声破棄、Spout破棄・送信失敗、OMT破棄は0でした。OMT受信器は先頭120秒で映像2,966フレームと32チャンネル音声5,931パケットを受信し、0番・31番の信号を確認しました。各系列のタイムスタンプ逆行は0、最大間隔は映像40 ms、音声20 ms、先頭から終端までのタイムスタンプ幅は両方とも118.6秒でした。SRT切断と再接続も成功しています。送信側・音声デバイス・OMT受信器はいずれも同じPC上で、実配線の時差や別クロック間の長時間同期までは証明しません。

Debugビルドで1時間のSRT→仮想WASAPI→Spoutループバックを実行しました。最初の接続で音声172,339,052フレーム、Spout映像89,968フレームを出力し、PortAudio underflowとSpout送信失敗は0でした。約6分時点のPC負荷上昇でSRT受信キューが最大575 msになり、音声14,825フレーム（再生フレーム比0.0086%）とSpout映像1フレームを破棄しました。その後、破棄は増えていません。クロック補正器は安定状態を維持し、ログ上のキュー先行量の基準からの誤差は最大2.44 ms、終盤は0.29 ms、音声とSpoutの推定時差は最大17.97 msでした。PortAudio報告DAC時刻の後退は211回、音声タイムラインの無音読取は412,468フレームでした。SRT切断後の再待受と短い再接続も確認しました。`scripts/test-srt-hour.ps1 -AnalyzeOnly` は保存ログを再集計し、`build/tests/srt-hour/summary.txt` に判定値を出します。この試験は同一PC内のソフトウェア経路であり、独立クロックの実機や物理的な表示・DAC時差を証明しません。

音声復帰の短時間試験では、VB-Audio Virtual CableのWASAPI排他出力を別プロセスが8秒間占有しました。ROODは `Pa_OpenStream: Invalid device` を記録し、1秒間隔で同じ名前・ホストAPIの出力を探して再試行しました。7回目の開設で復帰し、最初のSRT接続が切れる前に音声コールバックとデコード済みフレームの消費を確認しました。これは開設時の利用不可からの復帰であり、再生中の物理的なデバイス切断を証明しません。

復帰処理は受信統計の更新時にも音声ストリームの稼働状態を確認し、対応する音声フレームが一時的に来なくても再開設を試みます。正常なSRT切断ではPortAudioの停止結果を確認し、失敗時は現在の出力を破棄して再開設対象にします。変更後、上記の排他占有からの復帰試験と20秒のWASAPI・Spout・32チャンネルOMT同時出力試験を再実行して通しました。稼働中の機器切断による実エラー経路は未検証です。

PortAudioがストリームを稼働中と報告したままコールバックが停止する場合にも備え、最後のコールバックから2秒を超えたら出力を破棄して再開設を試みる監視を追加しました。通常の22秒SRT→WASAPIループバックでは `callbackStalled=0` のまま、SRTの切断・再接続と音声出力が通りました。8秒間の排他占有からの復帰試験も再実行して通りました。この結果は監視が正常再生を妨げないことと既存の復帰経路を確認するもので、実際にコールバックが停止するドライバ故障や稼働中の物理切断を再現したものではありません。

Windowsでは[WASAPIのエンドポイントID](https://learn.microsoft.com/en-us/windows/win32/api/mmdeviceapi/nf-mmdeviceapi-immdevice-getid)を取得し、選択した出力先を番号ではなくIDで再探索するようにしました。GUIで更新後に出力先が一時的に消えていても選択を残し、受信開始後に再試行します。Releaseビルドで、存在しない番号999と実在する仮想ケーブルのIDを同時指定した20秒のSRTループバックでは、最初の接続で音声179,745フレーム、再接続後に合計261,825フレームを再生し、`deviceAvailable=1`、PortAudio underflowと音声フレーム破棄は0でした。IDだけを指定して音声を再生する試験も通しました。存在しないIDだけを指定した試験では、出力の再開設を8回試しながら、SRTの映像194フレーム・音声462フレームをデコードし、切断後の再接続も継続しました。既存のWASAPI排他占有からの復帰試験も再実行して通しました。これらは番号変化と開始時のデバイス不在を模擬した試験で、稼働中の物理切断後の復帰は未検証です。ログは `build/tests/stable-device-id`、`build/tests/device-id-only`、`build/tests/unavailable-device-id` に保存しました。

ループバック送信に使うFFmpegのSRT callerは、待受中でも初回接続が時々失敗しました。検証スクリプトは短い間隔で最大3回再試行します。libsrtの切断・再接続条件と失敗理由は、接続監視を仕上げる際に調査します。

| 項目 | 方法 | 合格判断に必要な記録 |
| --- | --- | --- |
| ASIO多チャンネル | 実際に使用するASIOドライバで4/8/16chを列挙・形式確認し、全チャンネルに識別信号を出す | デバイス名、ドライバ版、利用可能数、割り当ての実出力 |
| WASAPI共有／排他 | 同一機器で希望サンプルレート・チャンネル数・バッファ長を確認 | 開閉成否、報告遅延、連続出力時のunderflow |
| 出力時刻精度 | コールバック時刻と `outputBufferDacTime` の連続性を記録し、可能ならループバックで物理出力と照合 | ずれ・ジッター・後退・欠落の分布 |
| 長時間同期 | 送信側と別クロックで1時間以上のSRT入力を再生し、音声・映像の時差を継続記録 | ドリフト量、補正量、最終的な時差 |
| デバイス切断復帰 | 再生中の切断、既定デバイス変更、同名再接続を試す | エラー遷移、無音化、再列挙と復帰の所要時間 |

上記が通るまで、PortAudioを最終採用と宣言しません。タイムスタンプはPortAudio APIが示す「先頭サンプルのDAC出力予定時刻」で、ここで実測した物理時刻ではありません。[PortAudioの時刻情報](https://portaudio.com/docs/v19-doxydocs/structPaStreamCallbackTimeInfo.html)。

実機ASIOの最初の検査には `scripts/probe-asio-msvc.ps1` を使います。指定したドライバだけを列挙し、無音出力の実効コールバック速度と申告レートを比較します。処理が止まるドライバに備えて時間制限を設けています。Voicemeeter Virtual ASIOを8チャンネル・44.1 kHzで3秒試したところ、実効約24.4 kframes/sで失敗と判定することを確認しました。これはチャンネルごとの物理配線や再生中の機器切断を代替する試験ではありません。
